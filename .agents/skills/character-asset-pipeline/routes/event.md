# Ancient/Event Art and Miniatures

Use this route for an Ancient or other event owner's main painting, canonical event base, or dialogue/history/map miniature. Ancient full-art **cards** use [the card route](cards.md). Read the requested topic reached through that owner's art/asset indexes, [ARTS.md sections 1–4](../../../../ARTS.md), [the shared workflow](../workflow.md), and the active [engine section](../engines.md). Apply the [missing-guide procedure](../../../../docs/conventions/documentation/character-guides.md#owners-without-art-guides) when the owner lacks a specification.

## Event Painting and Canonical Base

1. Resolve the event scene's native display area, aspect ratio, alpha/background needs and UI overlap from the owner's event specification and runtime mapping. A canonical `base.png` can be a complete scene. Use the event contract; standing sprite proportions, ground lines and ARTS.md 5.1 margin measurements apply only to standing work.
2. Open the identity and rough/motif inputs plus a same-use-case official event reference. When establishing a first base, use supplied identity references and settled decisions; when revising, preserve the approved base's identity. Record the actual input roles and [rough landmarks](../references.md#1-d-rough-sketch-or-reference-image--finished-asset-refs-or-draftsguidepng). Prompt the intended camera, subject extent, surroundings, palette, native display ratio and complete-painting output without baked-in UI or text.
3. Generate for that composition, then review the full image and its actual event display with UI overlap using the shared review loop. Preserve the complete painting through proportional Fit; record any approved background padding in the delivery page. Existing user-approved canvas boundaries remain part of the brief, not an instruction to crop further.
4. Promote a canonical base or runtime event texture only within the user's application authority. Record source identity, dimensions, conversion and scene mapping in the owner's event assets page; consult its API page only when wiring changes.

## Dialogue, History and Map Miniatures

1. Read the owner's UI specification and native consumers for dimensions, visible character extent, background and outline thickness. Open the approved identity anchor and a same-use-case official miniature at native display size. Do not inherit a player's portrait size or output list from another owner.
2. Generate a separate miniature composition with the requested visible head/body scope, expression, margins and alpha contract. Use the owner's canonical colors and anatomy within the shared chibi scope. Preserve the entire miniature; the main event painting supplies identity rather than a region to extract.
3. Inspect the complete image and native-size preview, resize the whole painting proportionally, and derive any required outline from the final alpha. Use the existing [conversion commands](../scripts/conversion-tools.md) with the owner's dimensions. Confirm every requested consumer uses the intended exports and record the result in its UI assets page.

Selected-image edits, comparisons and conversion-only requests use [the review route](review.md) with these event/UI contracts. Keep shared package and installation records in [deployment status](../../../../docs/deployment-status.md).
